# CakeGame AI Bot v1 pro — 设计说明

> 目标：在**不破坏三套既有回归**、**不开放难度档位**、**不读取不可观测信息**的前提下，
> 交付一个比 `CakeGame AI Bot v1` 更强的新大脑 `cakegame_v1_pro`。
> 引擎 Godot 4.5.1 · 兵力构型不变（1~3 真人 vs 1~2 Bot）· 局内 team play 不变。

---

## 1. 约束（不可违反）

| 约束 | 出处 | 含义 |
|---|---|---|
| 难度不可调 | README / `BotRegistry` 头部注释 | 任何可调参数都留在 `Balance`，玩家 UI 够不到 |
| 不使用隐藏信息 | `BotBrain` 设计论点 | 只能读「屏幕上看得见」的东西 |
| Bot 只在 Host 运算 | README 网络章节 | pro 的算力开销必须压得住：每个敌人 × 每 Host 帧 |
| 单次 bot 决策 ≤ `AI_THINK_INTERVAL` 的一小部分 | 同上 | 多了会拖慢 60 Hz 物理步 |

**「可观测」的判据**：角色的动画/朝向/GUI 直接呈现出来的东西，即
`aim_dir`（朝哪看）、`is_gun_out()`（枪有没有掏）、`state_id()`（在走/挥刀/翻滚/被钩）、
`reload_left`（换弹动作）、`mag`（打空会空响）、`hp`（血条）、`i_frames`/`spawn_invuln`/`stun_left`（无敌与受创表现）、
以及所有人的位置与速度。v1 已经在读这些，pro 沿用，**不新增任何一类**。

## 2. 先量错：v1 的瓶颈到底在哪

不是"枪法不够好"。把真实数值代进去算一遍就知道方向错了。

### 2.1 散布根本不是主要误差来源

命中由两个半角决定：目标张角 `atan((hit_radius + BULLET_RADIUS) / d)`，与枪口锥角 `GUN_SPREAD_DEG + gun_bloom`。

| 距离 d | 目标张角 | 散布锥角（bloom 0 / 3） | 纯几何命中率 |
|---|---|---|---|
| 58 px（贴脸） | 7.27° | 3° / 6° | **100% / 100%** |
| 92 px（交战带外沿） | 4.60° | 3° / 6° | **100% / 77%** |
| 140 px | 3.02° | 3° / 6° | **100% / 50%** |
| 192 px（v1 的开火上限） | 2.21° | 3° / 6° | **74% / 37%** |

> 结论：在 v1 自己维护的 58~92 px 交战带里，**哪怕散布拉满，纯几何命中率也有 77%~100%**。
> 换句话说：散布是次要矛盾。往"更精确地压枪"使劲，收益是边际递减的。

### 2.2 真正的误差来源是「目标会不会在飞行途中改变轨迹」

子弹 320 px/s，人 57.6 px/s（翻滚 132）。作战距离 90 px 时飞行时间 0.28 s，
这段时间里一个横向机动的人能位移 **16 px** —— 是目标轮廓（7.4 px）的 **2.2 倍**。

于是命中率其实是两件事相乘：

```
P(命中) = P(几何命中率) × P(目标在这 0.28 s 内没有剧烈改变轨迹)
                        ↑ 这一项才是主导
```

而**人（和 v1 bot）几乎总会在被击中之前改变轨迹**——一次翻滚就是 45 px 位移。
所以第二项才是胜负手，而它恰好完全由**角色的状态机承诺**决定：

> **第二个因子什么时候会接近 1 —— 答案是：当目标处在「承诺窗口」里时。**
> 角色处在翻滚、翻滚恢复、挥刀、抓钩硬直之中时，它既躲不掉，轨迹又是确定的。

### 2.3 由此得到的核心论点

> **更强的方向不是"把它打得更快"，而是"把子弹打进对手无法闪避的时间窗口"。**
> pro 的全部设计都围绕这一条：识别承诺窗口 → 攒着火 → 窗口一到就该必中。

## 3. 承诺窗口表（全部可从动画读出）

| 窗口 | 触发（可观测） | 时长 | 他能翻滚吗 | 轨迹确定吗 | 怎么吃 |
|---|---|---|---|---|---|
| **翻滚体** | `state == "roll"` | 0.42 s | ❌ 在状态里 | ✅ 沿 `roll_dir` 直线 | 把提前量打在翻滚终点上 |
| **翻滚恢复** | roll 刚结束，`roll_cd` 还剩 ~0.90 s | **0.90 s** | ❌ 冷却中 | 部分（残余速度） | **最肥的窗口**，pro 优先在这里压满火力 |
| **挥刀承诺** | `state == "melee"` | 0.38 s | ❌ 0.22 s 前不可打断 | ✅ 沿 aim 突进 | 他开始挥就脱离弧线，0.22 s 后回头惩罚 |
| **抓钩硬直** | 被我钩中，`stun_left > 0` | 0.22 s | ❌ 硬直锁技能 | ✅ 被 260 速度拽过来 | 钩中 → 一步贴脸 → 挥刀连招 |
| **换弹** | `reload_left > 0` | 至多 1.40 s | ✅ **可以翻滚** | ✅ 通常几乎不动 | 可以打，但不值得为它贴身，谨防被反击 |
| **被钩拉拽** | `state == "hook_pull"` | ≤0.55 s | ⚠️ 可以翻滚断线 | ✅ 向锚点 | 看他不停地方向提前量打落点 |

> 注意「换弹」那一行：它**不是**承诺窗口，因为哪个角色都能在换弹途中翻滚走。
> v1 把「目标在换弹」当成可以贴脸挥刀的判据（`_wants_melee`），这在 1v1 里会吃亏——
> pro 要把它降级，只对真正的锁定窗口（翻滚恢复 / 挥刀恢复 / 硬直）做贴脸。

## 4. 八项升级

### U1 · Commitment Window Profiling（承诺窗口剖析）

给每个敌人维护一条轻量时间线：上次看到的 `state`、该状态的进入时刻、上次翻滚结束时刻。

```
vulnerable(t) = 大/┬  0 若在 window 内（不可翻滚）
                └  1 若 roll_cd > 0 但已出窗口（仍不可翻滚，但能动）
```

由此算出每个敌人的 `escape_readiness ∈ [0,1]`，直接驱动两件事：

- **开火闸门**：只在 `escape_readiness` 低（或顺 deliberate 的必中球）时倾泻；
- **目标选择**：同样血量、同样距离，优先打正在滚动的那个。

> 收益：把 σ4.2 节的命中率从「学报 30~40%」拉回到几何上限（77~100%）。
> 代价：每个敌人 6 个字段 + 一次状态比对，可忽略。

### U2 · Roll Landing scoring（翻滚=带无敌的位移，不只是抖一下）

v1 的翻滚是「垂直于对方瞄准轴抖一下」（`perpendicular_escape`）。这在开阔地上毫无收益：
抖完落点可能仍在对方十字线上，而且翻滚结束后自己**进入 1.32 s 不能再滚**的锁定窗口，
等于把自己的承诺窗口白送给对方（对手只要掐准了就能惩罚这一次翻滚）。

pro 改成：**在 12 个候选方向里挑一个「落点不再被瞄」的**。

```
落点 = pos + dir × 45 px            # ROLL_SPEED × ROLL_DURATION ≈ 45 px
score = 0
score -= 能看到这个落点的敌人数 × β_los
score -= |dist(落点, 主目标) − 交战带中心| × β_band
score += 落点贴掩体 ? β_covr : 0
否决：落点不可走，或落点撞墙
取 argmax score 的方向作为 roll 方向
```

> 收益：翻滚从"消耗"变成"赚取位移 + 破线"，同时避免把自己扔进 1.32 s 空窗。
> 代价：每次决策多 12 条 `_walkable` 查询 + 最多 12×敌人数条射线。这是我们唯一的重开销，见 §6。

### U3 · Bloom/Range 命中概率闸门

把 §2.1 的表做成函数：

```
H(d, bloom) = clamp( atan((t.hit_radius + BULLET_RADIUS) / d)  /  ((GUN_SPREAD_DEG + bloom)·π/180), 0, 1)
```

低于阈值就不开枪，改为走位接近。这条规则同时**反过来抑制远距离点射**：当 `gun_bloom`
已经堆起来、目标又偏远时，先等约 0.2 s 让散布自然回落（衰减 1.65 °/s）再扣扳机。

> 收益：不再 192 px 外扫空一整匣，减少"打到一半弹匣空 → 被迫在对方枪口下换弹"。
> 这是**把 DPS 换成几百毫秒的生存**，净收益为正（换弹 1.40 s 的裸奔代价太高）。
> 代价：短期内显得"不爱开枪"。所以门限必须基于几何算，不能拍脑袋。

### U4 · EMA 预判（而不是瞬时速度做提前量）

v1 用 `t.velocity`（瞬时）做提前量，第二阶项用相邻两次决策速度的差分估加速度。
问题：决策率 16.7 Hz，两次采样间隔 60 ms，差分出来的加速度噪声极大；而目标在
做正弦横移时，瞬时速度恰恰指向的是它马上要离开的方向。

pro 对每个敌人维护 `v_ema`（指数滑动平均，`α ≈ 0.45`）和 `lateral_acc`（对其横向分量再平滑），
用二者合成提前点。

> 收益：横向摆动的目标命中率显著提升（这是最容易翻车的一类目标）。
> 代价：目标突然改向时会有 ~2 帧滞后，靠 U1（只在承诺窗口火力全开）补回来。

### U5 · Melee-arc avoidance（躲开近战弧线）+ 挥刀后惩罚

**v1 完全没有这件事**，而近战是全场最大的单次伤害源（22，对比子弹 12、钩 8）。

- 敌人进入 `melee` 状态且我们在 `MELEE_RANGE + r` 内 → 立刻脱离其 `MELEE_HALF_ARC`（109° 大扇形）；
- `time ≥ 0.22 s`（进入可打断的后 0.16 s）+ 之后 0.55 s 冷却 → **回头给它枪/刀**。

> 收益：近距离伤亡断崖式下降 + 拿到一个反打节拍。
> 代价：需要估算"他在 melee 里待了多久"——用 tracked 状态进入时刻，不用读隐藏 CD。

### U6 · 多威胁矢量位置评分（替掉纯解析一行流）

v1 的走位是 `radial + tangent`（接近/远离 + 环绕）的解析式，**只考虑了一个目标**。
3 真人同时打过来时它就脸接侧面火力。

pro 改成**候选点打分**：在自己周围一圈取 12 个候选点，对每个点算

```
score = −β_band · |dist(点, 主目标) − band_center|        # 保持在 58~92
      − β_los  · （能看到这个点的敌人数，>1 重罚）          # 这就是"别被两个角度同时打到"
      − β_nuke · Σ(次要威胁到该点的倒数距离)
      + β_covr · （该点是否贴着掩体转角）
      + β_hook · （该点是否还能看到主目标，否则不能还击）
```

不可走的点直接否决。

> 收益：这是团队战里唯一能保证不被"包饺子"的机制。
> 代价：第二次 Uniform Raycast 开销（与 U2 共用采样预算）；也可能显得"很爱绕后"。

### U7 · 抓钩：从"接近工具"升级为连招与逃生

v1 只有一个用法：距离 > 122 px 时钩过去。

pro 加三种：

1. **必中连招**：目标 `roll_cd > 0`（躲不掉）且距离落在 40~116 px → 钩（8 伤 + 0.22 s 硬直 +
   拉过来）→ 一步贴脸 → 挥刀（22）。合计约 30~55 伤，在 1 s 内。
2. **墙钩逃生**：`hp < AI_RETREAT_HP` 且身边有可用的墙 → 朝墙钩，牵引最大 300 px/s × 0.55 s ≈
   **90 px 位移**，是翻滚（45 px）的两倍，而且还会保留动量；这是唯一能真正脱战的写法。
3. **惩罚换弹**：目标正在换弹且距离合适 → 钩过来打乱他的节奏（他要么被拽走，要么站在原地挨刀）。

> 收益：多一条 kill combo，也多一条真正能脱战的手段。
> 代价：钩子是一次性承诺（3.2 s CD），投出去之后整整 3.2 s 没有退路。所以门槛设得很死——
> 只在"能连招"、"真需要逃"、"对方在换弹且我不会被还击"三种情况下才投。

### U8 · 对手适应（dodge bias）

统计每个敌人在我们瞄过来之后向哪一侧翻滚，累积 `dodge_bias ∈ [−1, 1]`。
开火时把瞄点向它惯用侧偏移 `bias × 权重`，权重按它的翻滚频率给。

> 同时记录一件更重要的事：**如果对手是"见到就翻滚"型，我们不需要额外的佯攻逻辑。**
> 因为 U1 的规则（只打进承诺窗口）天然克制它——窗口里它翻不起来。
> 这条被记在这里，是为了说明为什么**没有**写"假瞄诱骗"那一套（见 §5 否决清单）。

## 5. 否决清单（以及为什么）

| 被否决的方案 | 原因 |
|---|---|
| **加难度滑块 / 给 pro 加"反应时间加倍"** | 违反 README 明写的约束：难度档位不存在。所有数字必须留在 `Balance`。 |
| **读敌方 `melee_cd` / `roll_cd` 数值本身** | 属于"对方 UI 上的隐藏数字"。pro 只从 `state_id()` + 状态持续时间推断，二者天差地别——前者是开挂的缺口，后者是看动画。 |
| **全局路径规划（每帧 A\* 到最优埋伏点）** | 现在的 A\* 只在直线被挡时才启用，且 0.32 s 刷新一次，已经是 Continuum你我伺服器能接受的量；每帧全图 A\* 会让 Host 在 3 真人 + 2 Bot 构型下掉帧。 |
| **行为树 / GOAP 框架** | 这个项目现有的「优先级 + 意图旗标」结构（见 `BotV1.decide()` 的 5 段注释）已经把决策压在一个可读的线性流水线里；换框架要重写 `bot_brain` 的全部工具函数，收益却只是"更好看"。Breaking change 配不上收益。 |
| **假瞄诱骗（故意把准星偏开再拉回）** | 只对"见到就被吓到翻滚"的对手有用，而这类对手已经被 U1 克制；额外的偏摆还会污染 `aim_lock` 的开火窗口，风险高于收益。 |
| **机器学习 / 强化学习** | 需要训练管道、模型文件与 nol determinism（破坏"同 seed 同结果"的可复现性）。项目 Bettyheadless 回归依赖确定性 RNG seed（`BotBrain.setup` 按 actor_id 播种）。 |
| **让 pro 直接改 `bot_v1.gd`** | 两个大脑必须能同场对决才量化得出强弱，也必须允许玩家在设置里换回 v1。所以是新文件 + 注册表项，不是替换。 |

## 6. 性能预算

决策率 16.7 Hz（60 ms 一次），瞄准 60 Hz（只写 `aim_dir`，零开销）。

| 开销项 | 每次决策次数 | 说明 |
|---|---|---|
| `visible_enemies()` 视线 | ≤ 3 | 基线已有，不新增 |
| 承诺窗口更新 | ≤ 3 × 6 字段 | O(敌人数)，纯算术 |
| 翻滚落点候选（U2） | 12 × (1 可走 + ≤3 射线) | ≤ 48 rays |
| 走位候选（U6） | 12 × (≤3 射线) | ≤ 36 rays，与 U2 **共用采样环** |
| 合计 | **≤ ~90 条射线 / 60 ms** | 单个 Bot 约 1500 rays/s；Host 上 2 个 Bot 合计仍在余量内 |

> 实际实现里 U2 与 U6 **共用同一圈候选点**（一次采样两处用，省一半射线）。
> 并且敌人数为 1（最常见的构型）时自动走快路径：`_enemy_los_cache` 命中就跳过重复射线。

## 8. 怎么证明"更强"

不是靠我说。写了一个**无头对决基准** `tests/bot_duel.tscn`：

```bash
godot --headless --path . --fixed-fps 60 res://tests/bot_duel.tscn
```

- 自建最小场景（世界 + 竞技场 + 两个 BotActor），因为 `MatchDirector` 的名册只会用同一个
  `GameConfig.bot_version`，真实对局里两个不同大脑根本不可能同场；
- **两人放在不同队伍**（HUMANS vs BOTS），而不是开友伤——开友伤会连带翻转一堆无关行为；
- 每个 seed 跑**两遍并交换两边**，抵消出生半场与先手偏差；
- 阵亡后在**对手附近**重生（不是回老家），把"赶路"时间从采样里剔除。

### 实测结果（48 场 = 24 seed × 2 边）

```
cakegame_v1         5-12-31   win 10.4 pct (all)  win 29.4 pct (decided)
                    K/D 0.61   out-damaged opponent in 14.6 pct of duels
                    damage 3184   shots 797   damage per shot 33.3 of 12
                    rolls 673

cakegame_v1_pro    12-5-31   win 25.0 pct (all)  win 70.6 pct (decided)
                    K/D 1.64   out-damaged opponent in 37.5 pct of duels
                    damage 3604   shots 756   damage per shot 39.7 of 12
                    rolls 694
```

三个读数：

1. **子弹更少，伤害更多。** 756 : 797 发，换来 +13% 伤害。这是 U3 闸门按设计工作：
   本来要打空的那部分子弹，现在用于走位。
2. **每发伤害高 19%**（39.7% : 33.3%，分母是单发标称 12 点）。两边都免不了被墙角吃掉的
   子弹，所以这是"有没有停止浪费子弹"最干净的单一指标。
3. **决胜局 12-5**，K/D 1.64 : 0.61。多数对决 0-0——两个靠谱的 Bot 很难在 40 s 内
   杀死对方——所以单看胜场噪声大，这才要同时统计伤害。

### 两条方法学备注

会说谎的基准比没有基准更糟，所以这两条是硬要求：

- **锁死全局 RNG。** `ActorBody.fire_bullet()` 的散布用的是全局 `randf_range`，不是大脑
  per-actor 的 RNG。同一个 build 连跑两次，出来的是 12-2 和 6-6。脚手架里
  `seed(GLOBAL_SEED)` 之后，两次运行逐字节一致。
- **每帧采样交战状态。** 早期用种子地图时有过一串"0 伤害、0 开枪"的 0-0 —— 两人 40 s
  根本没遭遇。没有这一列，"他们没打起来"和"他们打成平手"看起来完全一样。
  后来改成开放竞技场 + 附近重生，才把非战斗时间压掉。
